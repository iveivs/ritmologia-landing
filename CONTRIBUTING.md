# Как работать с репозиторием

Короткие правила, чтобы история была чистой, а `main` всегда готов к выкладке.
Код — [`docs/ENGINEERING.md`](docs/ENGINEERING.md), дизайн —
[`docs/DESIGN-STANDARD.md`](docs/DESIGN-STANDARD.md).

## Как мы работаем (один разработчик)

Команды нет, поэтому процесс простой:

- **Обычная работа — прямо в `main`.** Маленькие правки коммитятся и
  пушатся в `main` без Pull Request. Каждый пуш автоматически проверяется
  (форматирование, линт, типы, сборка, UI-аудит) и **выкладывается только если
  всё зелёное**.
- **Ветка + Pull Request — только для рискованного:** крупный редизайн,
  замена Next.js, правка CI. Тогда проверки идут до выкладки, а сломанное не
  попадает на сайт. Имя ветки: `тип/кратко-через-дефис`
  (`feat/`, `fix/`, `style/`, `refactor/`, `docs/`, `chore/`); удаляется после
  слияния (Squash and merge).
- **Откат.** Что-то пошло не так — `git revert <коммит>` и пуш: прошлая
  версия вернётся на сайт. История не переписывается (`force push` по `main`
  не используем).
- Защита ветки `main` и обязательные ревью не нужны: некому и не с кем
  конфликтовать; роль «страховки» играют автоматические проверки и откат.

## Коммиты — Conventional Commits

```
тип(область): краткое повелительное описание, до 72 знаков

Зачем это сделано (если неочевидно). Что изменилось по сути.
```

Типы: `feat`, `fix`, `style`, `refactor`, `docs`, `chore`, `ci`, `perf`.
Область — по необходимости: `prices`, `footer`, `tokens`, `a11y`, `deps`.
Один коммит — одно логическое изменение; сообщение объясняет **почему**.
Если над кодом работал ИИ-ассистент, в конце добавляется строка
`Co-Authored-By: …`.

## Pull Request (когда он всё же нужен)

1. Маленький и про одно. Большая задача — несколько PR.
2. Заполни шаблон: что и зачем, как проверено, скриншоты **в обеих темах**
   (390 и 1280 px) для любых визуальных изменений.
3. CI должен быть зелёным: форматирование, линт, типы, сборка, `audit:ui`.
4. Тексты (копирайт) меняются только по запросу владельца — ссылка на запрос
   в описании.
5. Слияние — **Squash and merge** (один коммит на PR, заголовок PR — по
   Conventional Commits). Ветка удаляется.

## Что нельзя

- Делать `force push` по `main` и переписывать историю.
- Коммитить секреты, `.env`, большие неоптимизированные картинки.
- Добавлять зависимости без обоснования в PR.
- Менять токены «на глаз» (значения — решение по дизайну).

## Релизы и история изменений

- Все заметные изменения пишутся в [`CHANGELOG.md`](CHANGELOG.md) по формату
  [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/).
- Версии — `vMAJOR.MINOR.PATCH` (теги и GitHub Releases): `MAJOR` — смена
  дизайна/структуры, `MINOR` — новая секция или возможность, `PATCH` —
  правки и исправления.

## Автоматизация

- `.github/workflows/ci.yml` — проверки: `format:check`, `lint`, `tsc`,
  `build`, `audit:ui` на собранном сайте. Запускаются на каждом Pull Request и
  как первый шаг деплоя.
- `.github/workflows/deploy.yml` — на каждый пуш в `main` сначала запускает
  проверки, и только после них собирает и выкладывает сайт на GitHub Pages.
- Dependabot (`.github/dependabot.yml`) раз в неделю сам предлагает обновления
  npm и GitHub Actions в виде Pull Request: их можно прочитать и нажать
  «Merge» или закрыть.
