# Правила написания кода — «Ритмология»

Как устроен код и как его писать. Дизайн-правила — в
[`DESIGN-STANDARD.md`](DESIGN-STANDARD.md), процесс работы с GitHub — в
[`../CONTRIBUTING.md`](../CONTRIBUTING.md). Проверки этого документа
автоматизированы там, где это возможно (линт, типы, форматирование, сборка);
остальное — на ревью.

## 1. Стек и границы

Next.js (App Router, **статический экспорт** на GitHub Pages), React,
TypeScript `strict`, CSS Modules. Серверной части нет: нельзя API routes,
Server Actions, `cookies()`, рантайм-ISR. Сайт не собирает данные и не грузит
сторонний JS (см. стандарт, раздел 10).

## 2. Архитектура: слои и направление зависимостей

```
src/
  app/            маршруты, layout, metadata. Только сборка страницы.
  components/     секции лендинга: один файл = одна секция (+ свой .module.css)
    ui/           переиспользуемые примитивы (нужны минимум двум секциям)
  lib/            чистая логика и данные: content.ts, basePath.ts. Без React.
  styles/         tokens.css (токены), base.css (сброс), layout.css (утилиты)
scripts/          проверки и инструменты (token guard, UI audit)
docs/             стандарты; design-handoff/ — архив исходного дизайна
public/           статика (images/*.webp)
```

Зависимости идут **только вниз**: `app → components → components/ui → lib / styles`.

- `ui/` не импортирует секции; секции не импортируют друг друга.
- `lib/` не импортирует React и компоненты.
- Контент (тексты, списки, ссылки, цены, FAQ) живёт **только** в
  `lib/content.ts`, а не в JSX и не в CSS.
- Новый общий примитив появляется в `ui/`, когда он нужен второй секции
  (правило «двух использований»), раньше — остаётся в секции.

## 3. Компоненты

- Один компонент — один файл, имя файла = имя компонента (PascalCase),
  стили — рядом: `Name.module.css`. Именованный экспорт; `default` только для
  страниц/layout Next.js.
- **Серверные по умолчанию.** `"use client"` — только для интерактива
  (карусель отзывов, переключатель темы, карта по клику), и как можно ниже по
  дереву.
- Props типизируются явно; `any`, `@ts-ignore`, `as unknown as` запрещены.
  Типы props — рядом с компонентом.
- Размер: файл компонента до ~150 строк; больше — выделяй подкомпонент или
  данные в `content.ts`.
- Без inline-стилей (`style={{}}`), без «магических чисел» в JSX.
- Условный рендер читаем: ранний `return`/тернарник на один уровень; сложные
  условия выносятся в именованную переменную.
- Списки в разметке — семантические `ul/ol/li` (см. стандарт, раздел 7);
  `key` — стабильный идентификатор, не индекс, если порядок может меняться.
- Доступность — часть компонента, а не «потом»: `alt`, `aria-label` у
  иконочных кнопок, `aria-hidden` у декоративных SVG, достижимость с
  клавиатуры.

## 4. Стили

- Только **CSS Modules** и три глобальных файла из `styles/`. Селекторы —
  по классам (`.camelCase`), без `id`, без `!important` (единственное
  исключение — отключение transition при смене темы в `base.css`).
- Только токены (стандарт, раздел 1); локальные токены компонента называются
  по компоненту (`--btn-*`, `--card-*`).
- Адаптив — только `max-width: 900px` / `640px` (и `min-width: 901px` в
  `layout.css`). Новые брейкпоинты запрещены.
- Раскладка — утилитами из `layout.css`; отступы между соседями — `gap` /
  `.stack`, не `margin` у детей.
- Комментарий объясняет **почему**, а не что: нестандартное решение,
  оптическая компенсация, обход бага.

## 4a. Именование

| Что                 | Правило                          | Пример                          |
| ------------------- | -------------------------------- | ------------------------------- |
| Компонент, тип      | PascalCase                       | `PriceCard`, `ButtonProps`      |
| Функция, переменная | camelCase                        | `withBasePath`, `faqItems`      |
| Константы-данные    | camelCase (не SCREAMING)         | `telegramLinks`, `contactLinks` |
| CSS-класс (module)  | camelCase                        | `.priceRow`, `.linkActive`      |
| CSS-переменная      | kebab-case с префиксом по группе | `--space-4`, `--color-accent`   |
| Файл компонента     | PascalCase                       | `Platform.tsx`                  |
| Файл утилит/данных  | camelCase                        | `basePath.ts`, `content.ts`     |
| Изображение         | kebab-case, по смыслу            | `teacher-lesson.webp`           |
| Якорь секции        | kebab-case, английский, короткий | `#prices`, `#cabinet`           |

Импорты: алиас `@/` для всего из `src/` (не `../../`); порядок — внешние,
`@/…`, относительные, стили последними.

## 5. Данные и контент

- Тексты согласованы с владельцем; правятся только по его запросу (см.
  `AGENTS.md`). Факты (цены, условия, адрес) не выдумываем.
- Ссылки на Telegram — только из `telegramLinks`; контакты — из
  `contactLinks`. Не писать `https://t.me/…` в компонентах.
- Каждый путь к картинке — через `withBasePath()` (GitHub Pages живёт под
  `/ritmologia-landing/`).

## 6. Зависимости

- Рантайм-зависимости: `next`, `react`, `react-dom`. Любая новая — только с
  обоснованием в PR: зачем, размер, лицензия, поддержка, нельзя ли без неё.
- Версии `next` и `react` закреплены точно; обновления — отдельным PR
  (Dependabot присылает их сам), с зелёным CI.
- Запуск `npm audit` — часть ревью зависимостей: критичные уязвимости в
  рантайме закрываются, а если уязвимость не касается статического экспорта,
  это записывается в PR.
- Секретов в репозитории нет и быть не должно (`.env*` в `.gitignore`).

## 7. Ошибки и безопасность

- `localStorage` — только в `try/catch`, сайт работает без него.
- Внешние ссылки `target="_blank"` — только с `rel="noopener noreferrer"`.
- `dangerouslySetInnerHTML` — только для проверенных строк проекта (JSON-LD,
  скрипт темы), никогда для пользовательского ввода.
- Сторонние встраивания — только после действия посетителя.

## 8. Проверки (что запускать)

| Команда                                   | Что проверяет                                    |
| ----------------------------------------- | ------------------------------------------------ |
| `npm run lint`                            | ESLint + сторож токенов                          |
| `npm run format:check` / `npm run format` | форматирование Prettier (проверка / исправление) |
| `npx tsc --noEmit`                        | типы                                             |
| `npm run build`                           | сборка статического экспорта                     |
| `npm run audit:ui`                        | контраст, шкала, зоны нажатия, структура, ритм   |

Те же шаги выполняет CI (`.github/workflows/ci.yml`) на каждом PR; слияние
возможно только при зелёном CI.

## 9. Документация

Менял структуру, секцию, компонент или правило — обнови README, стандарт или
этот файл **в том же PR**. Устаревшая документация считается ошибкой.
